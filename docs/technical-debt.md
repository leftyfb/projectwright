## Architectural concerns

- **Planner/manager cycle.** The manager lazily imports the planner, while the planner imports configuration, validation, and queue helpers/constants from the manager. This makes either module difficult to reuse independently and makes module loading/test seams depend on import timing.
- **Manager/dispatcher contract remains a cross-script seam, now strict and documented.** The dispatcher accepts exactly one JSON object from manager `--once`, validates project identity, decision-specific fields, and decision/exit-code consistency before routing. JSON parsing rejects duplicate keys and any extra stdout; diagnostics belong on stderr. Exit codes are specified in `docs/baseline-validation.md`. This reduces ambiguity but does not replace the scripts with a typed shared API.
- **Hermes-specific coupling.** The planner and worker execute Hermes CLI commands directly. The dispatcher imports scripts from a configured directory, and the Hermes callback adapter imports sibling modules. A standalone runtime needs explicit model-runner, scheduler, approval, and notification interfaces.
- **Flat-script import layout.** The implementation is a set of scripts, not a packaged Python module; dynamic file loading and `sys.path` modifications assume sibling modules are installed together under `~/.hermes/scripts`.
- **Path conventions vary.** Some paths derive from `HERMES_PROJECT_CONFIG_DIR`, others default to `~/.hermes/projects`, and milestone/approval helpers use `Path.home() / '.hermes/projects'` directly. `pw_dispatch.py` accepts a scripts directory separately. This weakens relocatability and makes isolated test roots harder to apply consistently.
- **Repeated persistence primitives.** Journal, progress, recovery, planner, Telegram state, notes sync/publisher and milestone acceptance each implement their own lock/atomic-write logic. The patterns may be correct locally, but there is no shared contract for fsync, permissions, recovery from interrupted replacement, or lock ordering.
- **Repeated policy checks.** Manager, planner, worker and Telegram approval each re-check overlapping milestone, acceptance, quota and state conditions at different boundaries. This is a useful fail-closed defense, but duplicated logic can diverge unless a shared decision contract is tested.
- **Telegram recipients now share one strict contract.** `TELEGRAM_ALLOWED_USERS` is a comma-separated list of unique positive decimal user IDs; whitespace around entries is trimmed, while empty, duplicate, zero, signed, or non-decimal entries are rejected. Callback authorization and private-chat checks use the shared parser. Outbound approval messages target only parsed IDs and persist delivery state per recipient; retry skips recipients whose success marker exists. Telegram acceptance and local marker persistence are not atomic, so a failed marker write after an accepted send can cause a duplicate on retry. Delivery is at-least-once across that window; tests use injected transports only.
- **Task result and delivery result are coupled.** `project_task_worker.py` persists task completion/progress, then returns 1 when Telegram delivery fails (`process_once`, lines 752–755). `tests/integration/test_worker_delivery_contract.py::WorkerDeliveryPersistenceTests.test_delivery_failure_does_not_roll_back_persisted_task` verifies persistence in a disposable repository and confirms the failure exit. A caller must not interpret that exit as evidence that the task was rolled back; the status contract should separate execution outcome from notification outcome.
- **Timeout budgets are fragmented.** The timer-generated systemd service has `TimeoutStartSec=45min`; nested planner, worker and manager child timeouts are set separately. The combined execution/re-entry path should be checked against the service deadline; individual child limits do not establish an aggregate bound.
- **Hermes and systemd are runtime prerequisites.** The unit utility generates systemd user units; the active notification timer is separately provisioned. Packaging and unit lifecycle are not represented as an installable application contract.
- **External interfaces are only partially declared in repo metadata.** The development `pyproject.toml` and Debian control include basic Python/Git packaging, but optional integrations, runtime providers and fully supported CLI/API compatibility are not yet documented as a complete installation contract. Runtime depends on Hermes, Git, systemd, HA HTTP, Telegram Bot API and the Telegram Python library.

## Classification and confidence

No module is proven legacy or unused. `pw_project_timer.py` has no normal-flow caller observed and is classified as a manual operations utility, not as dead code. The checked-in manifest pins the source hashes and expected installed paths; a separate read-only runtime inspection compared the installed copies and reported parity for all 18 scripts. Neither result proves that each script executes. Actual usage is established only for the enabled plugin, active notification timer/service, disabled worker timer/service definition, and direct source call paths documented in `docs/component-inventory.md` and `docs/runtime-entrypoints.md`.

## Questions to resolve before refactoring

- Is the missing queue for the `projectwright` config intentional because this repository is being audited outside Projectwright, or should this config become a runnable project later?
- For quota, a project-level `rate_limited_entity` wins; omitted uses `PROJECTWRIGHT_RATE_LIMITED_ENTITY` when set and otherwise disables only the optional rate-limit gate. Explicit `null` always disables that gate. The required remaining-quota check remains fail-closed.
- Which system is authoritative for scheduling in standalone mode: per-project systemd timers, Hermes cron, or an internal scheduler?
- Is Telegram approval required core policy or a replaceable user-facing adapter? Which operations must remain operable without the Hermes gateway or Telegram library?
- The `--once` JSON/exit-code contract is specified in `docs/baseline-validation.md` and regression-tested. A typed shared API and stable persistence formats remain refactor questions.
- Which installed scripts are expected to be user-invocable, and which are internal-only? There is no packaging/CLI compatibility specification.
